# Chery Pulse

Личное SSR-приложение для двух пользователей: состояние автомобиля StarLine, журнал поездок, журнал запросов к API и Telegram-бот. Веб-процесс работает только с SQLite и очередью `jobs`; все обращения к StarLine и Telegram выполняет отдельный worker. Журнал API хранит адрес, метод, статус, длительность, заголовки и тела запросов/ответов StarLine; секретные значения автоматически маскируются.

## Требования

- Windows 11 для разработки
- Node.js 22 LTS (`.nvmrc`)
- npm

## Первый запуск

1. Скопируйте `.env.example` в `.env` и замените `NUXT_SESSION_PASSWORD` и пароли двух пользователей.
2. Выполните `npm install`.
3. Выполните `npm run db:migrate`.
4. Выполните `npm run seed`.
5. Запустите в двух терминалах `npm run dev` и `npm run worker`.
6. Откройте `http://localhost:3000`.

По умолчанию `STARLINE_MODE=fixture`: сеть StarLine не используется, данные читаются из безопасного примера `fixtures/starline-device.example.json`. Для `STARLINE_MODE=live` заполните реквизиты без `STARLINE_DEVICE_ID` и выполните `npm run starline:setup`. Команда интерактивно обрабатывает CAPTCHA или SMS-код, сохраняет токен пользователя в SQLite и выводит доступные `STARLINE_DEVICE_ID`. Одноразовый `npm run starline:probe` проверяет уже настроенное устройство и сохраняет сырой ответ в игнорируемый Git файл `fixtures/starline-device.json`; после этого этот файл можно использовать как `STARLINE_FIXTURE_PATH`.

## Команды

- `npm run db:generate` — создать миграцию после изменения схемы.
- `npm run db:migrate` — применить миграции.
- `npm run seed` — создать или обновить две учётные записи из `.env`.
- `npm run worker` — worker и Telegram long polling в watch-режиме.
- `npm run worker:start` — worker без watch-режима для production.
- `npm run worker:once` — обработать одну готовую задачу (удобно для smoke-проверки).
- `npm run starline:setup` — пройти интерактивную авторизацию StarLine, включая CAPTCHA/2FA, и получить `device_id`.
- `npm test` — модульные тесты парсера, сопоставления чеков и импорта почты.
- `npm run typecheck` — проверка Nuxt и worker TypeScript.
- `npm run build` — production-сборка Nuxt.
- `npm run smoke` — проверить собранный сервер, 401 без сессии, вход и защищённый дашборд.

## Telegram-уведомления

Укажите токен бота в `TELEGRAM_BOT_TOKEN`, а разрешённые username — через запятую в `TELEGRAM_ALLOWED_USERNAMES`, например `@gladyshev,@family_user`. Числовые Chat ID в env не хранятся. Каждый получатель должен открыть личный чат с ботом и один раз отправить `/start`: бот проверит username по белому списку и сохранит Chat ID в SQLite.

Если прямой доступ к Telegram ограничен, задайте `TELEGRAM_PROXY_URL`. Поддерживаются HTTP(S) и SOCKS5-прокси, в том числе с авторизацией: `http://user:password@host:port` или `socks5://user:password@host:port`. Спецсимволы в логине и пароле должны быть URL-кодированы. Прокси применяется только к Telegram Bot API и не влияет на StarLine или веб-приложение.

Обычные уведомления и отчёты отправляются без звука. При остатке топлива строго меньше 15 л worker ежедневно в 15:00 по московскому времени присылает звуковое напоминание заправиться. Worker также автоматически присылает отчёты:

- ежедневный — в 15:00 за предыдущий день;
- еженедельный — в понедельник в 15:00 за предыдущую неделю;
- ежемесячный — первого числа в 15:00 за предыдущий месяц.

В отчёт входят поездки, пробег, время в пути, топливо и расход, прогревы и их стоимость, заправки, состояние АКБ и последний снимок состояния автомобиля. Те же сводки доступны командами `/day`, `/week` и `/month`.

## Стоимость прогревов

Прогрев — это работа двигателя без движения: и утренний прогрев на холодную, и ожидание в машине с заведённым мотором. На главной и в отчётах он выводится в рублях.

Прогревом считается сессия двигателя, за которую одометр не сдвинулся. Одометр здесь — единственная надёжная мера: показания он отдаёт кусками по десять-двадцать километров примерно раз в десять минут, но при выключении зажигания всегда досылает накопленное, поэтому сессия, начавшаяся и закончившаяся на одном показании, действительно никуда не ездила.

Колонка `warmup_minutes` для этого не годится и не используется. Она хранит время до первого замеченного прироста пробега, а прирост появляется тогда, когда OBD в следующий раз заговорил об одометре, а не когда машина тронулась: сессия, где двигатель вышел на рабочую температуру за полторы минуты, получает в этой колонке девять с половиной.

### Откуда берутся литры

Датчик топлива меряет шагом в 1 % бака — это половина литра. Прогрев сжигает примерно 0,1–0,2 л, то есть впятеро меньше одного деления, так что по отдельной сессии израсходованное не измерить вовсе. Поэтому литры не считываются, а считаются по расходу на холостом ходу, а сам расход измеряется сразу по всем стоячим сессиям за всю историю: суммарное падение уровня делится на суммарные минуты.

Округление каждого показания даёт ошибку, и на два показания сессии её приходится вдвое. Ошибки независимы, поэтому суммарная растёт не как число сессий, а как корень из него — в отличие от самого расхода, который растёт линейно. Замер поэтому со временем становится точнее, и приложение принимает его, только когда погрешность опускается ниже 35 % измеренного падения; до тех пор берётся 0,8 л/ч — типичное значение для прогретого бензинового двигателя 1,5–2,0 л. Что именно сейчас используется, написано под цифрой на карточке, а у измеренного расхода дополнительно показан разброс в рублях.

Цену литра дают заправки того же периода: сумма чеков, делённая на их объём. Если в периоде заправок не было, берётся последняя известная цена до его конца, и это отмечается в подписи. Без единого чека стоимость не показывается совсем — вместо рублей выводится время.

### Прогрев, который закончился поездкой

Такой прогрев прячется внутри сессии, которая всё-таки поехала, и момент отъезда в данных ничем не отмечен: одометр отчитывается кусками, `position.s` всегда ноль, а фикс по вышкам отстаёт от машины на три-четыре минуты. Отставание именно измерено, а не предположено: окно «до отъезда» по координатам жжёт 5,1 л/ч при эталоне холостого хода 0,70 л/ч и езды 4,1–6,7 л/ч — в эти минуты машина уже ехала. Подставив те же эталоны в баланс, на все 25 таких сессий получаем не больше восьми минут скрытого простоя суммарно, то есть по двадцать секунд на поездку.

Точный ответ даёт охрана. Ехать на охраняемой машине нельзя, поэтому `state.arm` при работающем двигателе — это прогрев без всяких оговорок. Признак ловит только дистанционный пуск: когда прогреваются, сидя за рулём, охрана уже снята дверью. Но именно автозапуск и есть тот прогрев, который заканчивается поездкой, — снятие с охраны в этот момент и означает отъезд.

Минуты считаются по снапшотам: интервал засчитывается, только если на обоих его концах двигатель работает и охрана включена, а разрывы длиннее пяти минут не учитываются — при заведённом двигателе опрос идёт каждые тридцать секунд, и большая пауза означает остановку worker'а, а не работу на месте. Внутри сессий, которые никуда не ехали, эти минуты не берутся: те сессии учтены целиком по таблице, и второй раз платить за них не нужно.

### Чего цифра не учитывает

Прогрев за рулём, закончившийся поездкой, в счёт по-прежнему не попадает: охрана в этом случае снята, а других признаков нет. По летним данным таких минут почти нет, зимой их будет больше. Итог поэтому остаётся нижней оценкой.

Температура охлаждающей жидкости на старте сессии сохраняется в `engine_temp_start` и делит прогревы на холодные и на запуски уже прогретого двигателя. На саму стоимость она не влияет — только на разбивку.

## Подтверждение заправок чеками

Заправка считается подтверждённой, если к ней привязан чек. Чек — самостоятельная запись: письмо или фото приходит раньше, чем датчик топлива заметит прирост, поэтому непривязанные чеки ждут своей заправки в разделе «Чеки».

Чек попадает в приложение тремя путями:

- **Почта.** Worker раз в `IMAP_POLL_MINUTES` минут читает ящик, берёт письма только от отправителей из `IMAP_SENDER_ALLOWLIST` и сохраняет вложение либо само письмо как HTML-файл. Повтор отсекается по `Message-ID` и по SHA-256 содержимого.
- **Telegram.** Пришлите боту фото чека: он читает QR-код, достаёт дату и сумму, а недостающий объём спрашивает следующим сообщением.
- **Вручную.** Кнопка «Добавить чек» на странице «Чеки» — для наличных и бумажных чеков, с камерой телефона или выбором файла. На карточке заправки по-прежнему можно просто прикрепить файл.

Письмо разбирается универсальными правилами, проверенными на настоящих чеках двух операторов — «Первого ОФД» (Роснефть) и «ОФД-Я» (Лукойл). Дату и сумму даёт фискальная ссылка или QR-код, строку позиции — вид топлива, цена и объём.

Единицы измерения в чеке не печатаются вовсе: Роснефть выводит `АИ-92-К5 N 2:00000 64.25 20 1285.00`, Лукойл — `41.38 x 61.26 = 2534.94` отдельной строкой под названием топлива. Поэтому тройка «цена, объём, сумма» опознаётся по арифметике: произведение первых двух должно равняться третьему. Какое из чисел цена, решает объём бака — 61,26 л в него не поместится, значит это цена. Если письмо не распозналось, чек всё равно сохраняется и ждёт ручного заполнения.

Документом чека сохраняется PDF, если он приложен, иначе само письмо. QR-код читается и из вложения, и из `data:`-картинки внутри HTML, но документом не становится.

### Чек важнее датчика

Датчик топлива StarLine ошибается на литр-полтора: при заправке на 20 л он может показать 21. Поэтому как только чек привязан к заправке, её объём, сумма, цена, АЗС и вид топлива берутся из чека. Исходное показание датчика не теряется — оно сохраняется в `sensor_litres_added`, на карточке заправки выводится подписью «датчик показывал 21 л», а при отвязке или удалении чека возвращается на место.

Если заправку оплатили двумя транзакциями и к ней привязаны два чека, объёмы и суммы складываются, а цена за литр пересчитывается как сумма, делённая на объём. Отчёты и статистика расхода считают по исправленным значениям, поэтому подтверждённые чеками заправки точнее неподтверждённых.

Сопоставление считает совпадение по времени и объёму. Окно намеренно несимметрично: чек ищется в пределах 24 часов до момента, когда датчик сообщил о приросте, и 15 минут после — уровень топлива обновляется только на заведённом двигателе. Расхождение до 2 л или 15 % считается нормой датчика; если объём сравнить не с чем, чек не привязывается автоматически, а ждёт подтверждения человеком.

Из QR-кода бумажного чека доступны только дата и сумма — состава покупки там нет, его отдаёт лишь API ФНС, который в приложении не используется. Объём и цена вводятся вручную либо считаются из двух известных значений.

### Настройка почтового ящика

Заведите отдельный ящик Gmail или Яндекс, включите двухфакторную аутентификацию и создайте **пароль приложения** — он и указывается в `IMAP_PASSWORD`. В основном ящике настройте пересылку писем от АЗС и ОФД на служебный.

Разрешённый отправитель ищется по всем адресам письма: `From`, `Sender`, `Reply-To`, `Return-Path`, `X-Forwarded-For`, а также в блоке «`От:`», который почтовый клиент вставляет в тело при ручной пересылке. Последнее существенно: автоматическая пересылка правилом сохраняет исходный `From`, а пересылка кнопкой «Переслать» из Mail.ru переписывает все заголовки, и настоящий отправитель остаётся только в тексте.

Список по умолчанию уже содержит операторов, чьи письма проверены: `1-ofd.ru` — «Первый ОФД», через него приходят чеки Роснефти; `ofd-ya-kassa.ru` — «ОФД-Я», через него приходят чеки Лукойла. Обратите внимание, что письма ОФД-Я отправляются с домена `ofd-ya-kassa.ru`, а сайт оператора — `ofd-ya.ru`: в списке нужны оба.

У Proton нет обычного IMAP: понадобился бы Proton Mail Bridge на платном тарифе, запущенный рядом с контейнером.

Пока `RECEIPTS_MAIL_MODE=off`, задача опроса почты не планируется вовсе. Режим `fixture` читает `fixtures/receipt-mail.example.json` и позволяет проверить весь путь импорта без ящика.

## Production-развёртывание в Docker

В состав входят четыре production-сервиса: `web`, `worker`, одноразовый `migrate` и Caddy. Caddy принимает трафик на портах 80/443 и автоматически выпускает и обновляет TLS-сертификат. SQLite хранится в именованном volume `app-data`; наружу порт Nuxt не публикуется.

На Linux-сервере должны быть установлены Docker Engine и Compose plugin. До запуска направьте A/AAAA-запись домена на сервер и откройте входящие TCP-порты 80/443 и UDP-порт 443.

Первое развёртывание:

```bash
git clone <repository-url> chery-pulse
cd chery-pulse
cp .env.production.example .env.production
chmod 600 .env.production
# Заполните домен, секрет сессии, пользователей и реквизиты интеграций.

docker compose build
docker compose run --rm --no-deps migrate
docker compose run --rm --no-deps seed
docker compose up -d
```

Секрет сессии можно создать командой `openssl rand -base64 48`. Не используйте значения-заглушки из примера. Команда `seed` обновляет пароли существующих пользователей, поэтому запускайте её повторно только при намеренной ротации учётных данных.

Если StarLine запрашивает CAPTCHA или `STARLINE_DEVICE_ID` ещё неизвестен, остановите worker и запустите интерактивную настройку с подключённым production volume:

```bash
docker compose stop worker
docker compose run --rm --no-deps worker npm run starline:setup
# Скопируйте выведенный STARLINE_DEVICE_ID в .env.production.
docker compose up -d --force-recreate worker
```

При автоматическом деплое добавляйте к каждой команде Compose `--env-file .env.deploy`, чтобы использовался опубликованный tasks-образ. Токен пользователя сохраняется в SQLite; пароль и токены в терминал не выводятся.

Проверка состояния и просмотр логов:

```bash
docker compose ps
docker compose logs --tail=100 web worker caddy
curl --fail https://pulse.example.com/api/health
```

Для обновления приложения:

```bash
git pull --ff-only
docker compose pull caddy
docker compose build --pull
docker compose up -d
```

`migrate` запускается перед `web` и `worker`; миграции должны оставаться обратно совместимыми на время обновления. Не масштабируйте `worker` больше чем до одного экземпляра: очередь и Telegram long polling рассчитаны на единственный процесс.

Перед обновлением рекомендуется сделать согласованную резервную копию SQLite:

```bash
docker compose stop web worker
docker compose run --rm --no-deps migrate sh -c 'tar -C /app/data -czf - .' > chery-pulse-data-$(date +%F-%H%M).tar.gz
docker compose start web worker
```

Сертификаты Caddy находятся в volumes `caddy-data` и `caddy-config`. Они восстанавливаются автоматически, но volume `app-data` содержит незаменяемую историю и должен регулярно копироваться за пределы сервера.

## Автоматическое развёртывание

Workflow `.github/workflows/deploy.yml` запускается после каждого push в `main` и вручную через `workflow_dispatch`. Он выполняет тесты и typecheck, собирает два Linux-образа, публикует их в GHCR с неизменяемым тегом commit SHA и развёртывает релиз по SSH.

В GitHub Actions должны быть настроены repository secrets:

- `DEPLOY_HOST` — IP-адрес production-сервера;
- `DEPLOY_HOST_KEY` — строка `known_hosts` с подтверждённым ED25519-ключом сервера;
- `DEPLOY_SSH_KEY` — отдельный приватный SSH-ключ без passphrase, доступный только Actions. Соответствующий публичный ключ на сервере ограничен опциями `restrict` и `command`, поэтому не предоставляет интерактивный shell, SCP или port forwarding.

Перед миграцией `deploy/production-deploy.sh` останавливает `web` и `worker`, сохраняет согласованную копию SQLite в `/opt/chery-pulse/backups`, применяет миграции и ждёт healthcheck. При неуспешном запуске скрипт возвращает предыдущие образы. Автоматические резервные копии хранятся 14 дней; внешнее резервное копирование volume по-прежнему необходимо.

## Хранение данных

Снимки состояния автомобиля, поездки, журнал обращений к API и чеки хранятся бессрочно. Файлы чеков находятся в каталоге `RECEIPT_STORAGE_DIR` (по умолчанию `data/refuel-receipts`) и с включённым импортом из почты накапливаются сами — этот каталог нужно включить в резервное копирование наравне с файлом базы. В приложении нет фоновой очистки, TTL или ограничения истории по дате. Журнал поездок выводится постранично, поэтому все накопленные поездки остаются доступны независимо от их возраста.

Миграции и повторный запуск `npm run seed` не очищают историю. Для переноса или резервного копирования необходимо сохранять файл SQLite, указанный в `DATABASE_URL` (по умолчанию `data/app.db`). Просроченные токены StarLine могут заменяться или удаляться при повторной авторизации — это служебные учётные данные, а не история автомобиля.
