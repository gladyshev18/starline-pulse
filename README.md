# StarLine Pulse

> [!IMPORTANT]
> **Это неофициальный личный проект.** Он не является продуктом, приложением или сервисом поддержки StarLine и не связан с производителем или владельцами бренда StarLine. Название StarLine используется только для обозначения интеграции с охранно-телематической системой. Все товарные знаки принадлежат их владельцам.

StarLine Pulse — закрытое веб-приложение для личного контроля одного автомобиля. Оно собирает телеметрию StarLine, восстанавливает поездки и заправки, считает эксплуатационную статистику, хранит чеки и документы по обслуживанию и отправляет уведомления в Telegram.

Репозиторий открыт для хранения и разработки кода, но само приложение рассчитано на частное использование: все страницы и API, кроме формы входа и healthcheck, требуют авторизации.

## Возможности

- текущее состояние автомобиля: связь, зажигание, охрана, пробег, топливо, АКБ, температуры и уровень GSM;
- автоматическое восстановление поездок по телеметрии, пробегу и сессиям двигателя;
- история поездок с водителем, комментарием, длительностью, расстоянием и расходом;
- месячная статистика по пробегу, топливу, прогревам, средней скорости, стоимости километра и состоянию автомобиля;
- километры на моточас по неделям — сколько из работы двигателя досталось дороге, а сколько ушло на стояние;
- профиль использования по часам и дням недели, длительность простоев и дни без поездок;
- оценка достоверности расхода каждой поездки и поездки, выбивающиеся из своей корзины скорости;
- движение цены литра по чекам, сравнение АЗС и переплата за один и тот же бензин;
- убыль топлива на стоянке — по знаку изменений, а не по литрам, которые тонут в шаге датчика;
- стоимость километра с обслуживанием и постоянными расходами вроде страховки и налога;
- запас хода в километрах, в днях поездок и в дальних поездках — диапазоном, а не средним;
- учёт заправок и сопоставление показаний датчика с фактическими данными из чеков;
- загрузка чеков вручную, из Telegram и из отдельного IMAP-ящика;
- чтение QR-кодов чеков и разбор писем нескольких операторов фискальных данных;
- ресурс масла по трём шкалам сразу — пробег, моточасы и календарь — с той, что кончится первой;
- норма километров в сутки и фактический темп после замены: на сколько процентов пробег обгоняет время, сколько можно проезжать в день, чтобы дотянуть до срока, и когда замена при нынешней езде;
- журнал технического обслуживания и OCR заказ-нарядов с ручным подтверждением распознанных полей;
- журнал обращений к StarLine API с маскированием секретных значений;
- Telegram-бот со статусом автомобиля, последними поездками, отчётами, статистикой и напоминаниями;
- Docker-развёртывание с Caddy, автоматическим TLS и резервной копией SQLite перед миграциями.

## Как устроен проект

- **Nuxt 4** — SSR-интерфейс, авторизация и серверное API.
- **Worker** — единственный процесс для StarLine API, очереди задач, Telegram, IMAP и OCR.
- **SQLite/libSQL + Drizzle ORM** — телеметрия, поездки, пользователи, очередь и прикладные данные.
- **Telegram Bot API / grammY** — команды, отчёты, уведомления и загрузка фотографий чеков.
- **Tesseract.js, jsQR и Jimp** — OCR документов и распознавание QR-кодов.
- **Docker Compose + Caddy** — production-сервисы и HTTPS.

Веб-процесс не обращается к StarLine или Telegram напрямую. Он работает с SQLite и ставит задания в таблицу `jobs`; внешние интеграции выполняет worker. Такая схема не допускает параллельный polling и сохраняет очередь после перезапуска.

## Требования

Для разработки:

- Node.js 22 или новее;
- npm;
- Windows, Linux или macOS.

Для production:

- Linux-сервер;
- Docker Engine и Docker Compose plugin;
- домен с A/AAAA-записью на сервер;
- открытые TCP-порты 80/443 и UDP-порт 443.

## Локальный запуск

1. Установите зависимости:

   ```bash
   npm ci
   ```

2. Скопируйте `.env.example` в `.env`.

   PowerShell:

   ```powershell
   Copy-Item .env.example .env
   ```

   Linux/macOS:

   ```bash
   cp .env.example .env
   ```

3. Замените как минимум `NUXT_SESSION_PASSWORD` и пароли пользователей.

4. Подготовьте базу:

   ```bash
   npm run db:migrate
   npm run seed
   ```

5. Запустите два процесса в отдельных терминалах:

   ```bash
   npm run dev
   ```

   ```bash
   npm run worker
   ```

6. Откройте `http://localhost:3000`.

### Безопасный режим с тестовыми данными

В `.env.example` установлен `STARLINE_MODE=fixture`. В этом режиме проект не входит в аккаунт StarLine и читает обезличенный ответ из `fixtures/starline-device.example.json`.

Это рекомендуемый режим для разработки интерфейса, тестов и проверки миграций.

### Подключение StarLine

Для реального устройства установите `STARLINE_MODE=live`, заполните `STARLINE_APP_ID`, `STARLINE_APP_SECRET`, `STARLINE_LOGIN` и `STARLINE_PASSWORD`, затем выполните:

```bash
npm run starline:setup
```

Команда проводит интерактивную авторизацию, включая CAPTCHA или второй фактор, сохраняет токены в SQLite и выводит доступные `STARLINE_DEVICE_ID`. После выбора устройства добавьте его ID в `.env`.

Проверить настроенное подключение и сохранить ответ в игнорируемый Git-файл можно командой:

```bash
npm run starline:probe
```

Учётные данные, токены и реальные fixture-файлы нельзя коммитить в репозиторий.

## Настройки окружения

Полный список находится в `.env.example` и `.env.production.example`. Основные группы:

- `NUXT_SESSION_PASSWORD`, `SEED_USER_*` — вход в веб-приложение;
- `DATABASE_URL` — SQLite/libSQL;
- `STARLINE_*` — режим и доступ к StarLine;
- `TELEGRAM_*` — бот, разрешённые username и необязательный прокси;
- `RECEIPTS_MAIL_MODE`, `IMAP_*` — импорт чеков из почты;
- `RECEIPT_STORAGE_DIR`, `SERVICE_DOCUMENT_STORAGE_DIR` — файловое хранилище;
- `TESSERACT_CACHE_DIR` — кэш языковых моделей OCR;
- `APP_DOMAIN` — production-домен для Caddy.

Не используйте примеры паролей из env-файлов в production. Секрет сессии можно создать так:

```bash
openssl rand -base64 48
```

## Telegram-бот

Для запуска бота задайте `TELEGRAM_BOT_TOKEN` и перечислите разрешённые публичные username в `TELEGRAM_ALLOWED_USERNAMES`. Каждый получатель должен один раз отправить боту `/start`; после проверки username бот сохранит Chat ID в SQLite.

Основные команды:

- `/status` — состояние автомобиля;
- `/fuel` — сколько топлива нужно до полного бака;
- `/last` — последние пять поездок;
- `/stats [месяц]` — месячная статистика;
- `/day`, `/week`, `/month` — отчёты за завершённый период;
- `/receipts` — заправки, для которых не найден чек;
- `/menu` и `/hide` — показать и убрать кнопки меню.

Клавиатура с кнопками не закреплена: её сворачивают значком у поля ввода, а `/hide` убирает совсем — ни ответы, ни автоматические уведомления её не возвращают, это делает только `/menu`.

Worker автоматически отправляет ежедневные, еженедельные и ежемесячные отчёты, уведомляет о завершённых поездках, предлагает выбрать водителя и напоминает о низком уровне топлива. Доступ к боту ограничен списком username; группы не поддерживаются.

### Еженедельная подборка

Кроме табличных отчётов раз в неделю приходит подборка примечательного: рекорды, сравнение с прошлой неделей и с обычной, цена литра, прогревы, привычки использования. В отличие от отчётов её собирает не worker — текст пишется снаружи, а два скрипта дают материал и канал доставки:

- `npm run digest:facts` — печатает JSON с неделей, прошлой неделей, базой для сравнения, рекордами и текущим состоянием. Ничего не пишет и никуда не отправляет. Флаг `--last` берёт предыдущую полную неделю, `--weeks=12` меняет глубину базы;
- `npm run digest:send -- message.json` — отправляет готовый текст получателям бота. Файл содержит либо общий `text` с подстановкой `{name}`, либо `messages` с текстом на каждого получателя. Флаг `--dry-run` показывает, кому и что уйдёт, ничего не отправляя.

Скрипт отправки только шлёт сообщения и не слушает обновления, поэтому работает рядом с запущенным ботом. На production оба запускаются внутри контейнера worker из тома `/app/data`:

```bash
docker compose cp scripts/weekly-facts.ts worker:/app/data/weekly-facts.ts
docker compose exec -T worker npx tsx /app/data/weekly-facts.ts
```

## Чеки и документы

Чек можно:

- загрузить через веб-интерфейс;
- отправить фотографией Telegram-боту;
- получить из отдельного IMAP-ящика.

Приложение извлекает доступные реквизиты, ищет подходящую заправку по времени и объёму и оставляет сомнительные совпадения на ручное подтверждение. Данные из подтверждённого чека имеют приоритет над приблизительным изменением уровня топлива, но исходное показание датчика сохраняется.

Заказ-наряды хранятся отдельно от топливных чеков. OCR предлагает дату, пробег, сумму и номер документа; пользователь проверяет результат перед созданием записи о техническом обслуживании.

Для IMAP используйте отдельный почтовый ящик и пароль приложения. Импорт полностью выключен при `RECEIPTS_MAIL_MODE=off`.

## Команды проекта

- `npm run dev` — Nuxt в режиме разработки;
- `npm run worker` — worker в watch-режиме;
- `npm run build` — production-сборка веб-приложения;
- `npm run preview` — локальный запуск production-сборки;
- `npm test` — тесты Vitest;
- `npm run typecheck` — проверка Nuxt и worker TypeScript;
- `npm run db:generate` — создать миграцию Drizzle после изменения схемы;
- `npm run db:migrate` — применить миграции;
- `npm run seed` — создать или обновить две учётные записи из env;
- `npm run worker:start` — worker без watch-режима;
- `npm run worker:once` — обработать одно готовое задание;
- `npm run starline:setup` — интерактивно настроить StarLine;
- `npm run starline:probe` — проверить устройство и сохранить тестовый ответ;
- `npm run fuel:backfill` — восстановить литры из исторических процентов топлива;
- `npm run trips:recompute` — пересчитать поездки из сохранённой телеметрии;
- `npm run digest:facts` — материал для еженедельной подборки в виде JSON;
- `npm run digest:send -- message.json` — отправить готовый текст получателям бота;
- `npm run smoke` — smoke-проверка собранного сервера.

Команды `fuel:backfill`, `trips:recompute`, `seed` и миграции изменяют данные. Перед их запуском на production сделайте резервную копию SQLite.

## Production в Docker

В production используются сервисы:

- `migrate` — применяет миграции перед запуском приложения;
- `web` — Nuxt/Nitro;
- `worker` — очередь и внешние интеграции;
- `caddy` — HTTPS и reverse proxy;
- `seed` — служебный профиль для первоначального создания пользователей.

Первое развёртывание:

```bash
git clone https://github.com/gladyshev18/starline-pulse.git /opt/starline-pulse
cd /opt/starline-pulse
cp .env.production.example .env.production
chmod 600 .env.production
# Заполните .env.production, в том числе APP_DOMAIN.

docker compose build
docker compose run --rm --no-deps migrate
docker compose run --rm --no-deps seed
docker compose up -d
```

Проверка:

```bash
docker compose ps
docker compose logs --tail=100 web worker caddy
curl --fail https://pulse.igpx.site/api/health
```

SQLite, чеки, документы и токены находятся в volume `starline-pulse_app-data`. Volumes Caddy хранят TLS-сертификаты и конфигурацию. Основной volume необходимо регулярно копировать за пределы сервера.

## GitHub Actions

Workflow `.github/workflows/deploy.yml` при push в `main`:

1. устанавливает зависимости;
2. запускает тесты и проверку типов;
3. собирает образы `web` и `tasks`;
4. публикует их в GHCR;
5. развёртывает release по ограниченному SSH-ключу.

Для environment `production` или repository secrets нужны:

- `DEPLOY_HOST` — адрес сервера, например `pulse.igpx.site`;
- `DEPLOY_HOST_KEY` — строка `known_hosts` с публичным ED25519 host key сервера;
- `DEPLOY_SSH_KEY` — приватный ключ отдельной пары для GitHub Actions.

Серверный обработчик устанавливается командой `install -m 700 deploy/github-actions-command.sh /usr/local/sbin/starline-pulse-github-actions`. Публичная часть `DEPLOY_SSH_KEY` добавляется в `/root/.ssh/authorized_keys` с принудительной командой `/usr/local/sbin/starline-pulse-github-actions`. Этот ключ не должен давать интерактивный shell, SCP или port forwarding.

Deploy-скрипт принимает только образы `ghcr.io/gladyshev18/starline-pulse-web` и `ghcr.io/gladyshev18/starline-pulse-tasks` с тегом commit SHA. Перед миграцией он останавливает изменяющие базу процессы и создаёт согласованную резервную копию в `/opt/starline-pulse/backups`.

## Данные и безопасность

- пароли пользователей хешируются Argon2;
- сессия хранится в защищённой HTTP-only cookie;
- веб-страницы и прикладное API закрыты авторизацией;
- Telegram принимает команды только от настроенных username и сохранённых Chat ID;
- диагностический журнал маскирует токены, пароли, cookie и другие секретные поля;
- точные координаты и идентификаторы устройства не копируются в диагностический JSON;
- прикладные контейнеры `web` и `tasks` запускаются без root; сервисы используют read-only filesystem и урезанные Linux capabilities;
- исторические снимки, поездки, заправки и документы не имеют автоматического срока удаления.

Секреты всё равно находятся в `.env.production` и SQLite. Защита сервера, резервное копирование volume и контроль доступа остаются ответственностью владельца инсталляции.

## Ограничения

- проект разработан под одну личную инсталляцию, одно устройство StarLine и один экземпляр worker;
- структура ответов и авторизация StarLine могут измениться без предупреждения;
- расчёт поездок, расхода и прогревов зависит от частоты и точности телеметрии;
- OCR и автоматическое сопоставление документов требуют проверки человеком;
- это не противоугонный центр, не система экстренного реагирования и не инструмент диагностики автомобиля;
- проект не предоставляет SLA, официальную поддержку StarLine или гарантии совместимости с другими устройствами.
